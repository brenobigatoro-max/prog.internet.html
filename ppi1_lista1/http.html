HTTP na prática: requisição e resposta

Início | História da Web | Estados | Currículo | Contato

1. O papel do HTTP na Web

HTTP significa Hypertext Transfer Protocol, ou Protocolo de Transferência de Hipertexto. Ele define como clientes e servidores trocam mensagens para solicitar recursos, enviar dados e informar o resultado de uma operação.

Quando você visita uma página, o navegador solicita seu HTML. Ao interpretá-lo, pode fazer outras requisições para buscar imagens e demais arquivos. Uma página pode, portanto, depender de várias trocas de mensagens, inclusive com servidores diferentes.

HTML estrutura o conteúdo; HTTP organiza sua transferência. HTTPS utiliza os mesmos conceitos de requisição e resposta com proteção criptográfica em trânsito. Usar POST, sozinho, não criptografa os dados.

2. Cliente, servidor, requisição e resposta

Cliente
Programa que inicia uma solicitação. O navegador é um exemplo; aplicativos e ferramentas também podem ser clientes.
Servidor
Software que recebe solicitações e fornece respostas. Pode entregar um arquivo ou executar uma aplicação para gerar conteúdo. Não precisa ser uma única máquina.
Requisição
Mensagem enviada pelo cliente com um método, o recurso desejado, cabeçalhos e, quando aplicável, um corpo com dados.
Resposta
Mensagem do servidor com um código de status, cabeçalhos e, quando cabível, um corpo, como HTML, uma imagem ou dados.

O ciclo de comunicação

  1. O usuário informa uma URL ou aciona um link no navegador.
  2. Se necessário, o navegador resolve o nome pelo DNS e estabelece uma conexão com o servidor.
  3. O cliente envia a requisição HTTP.
  4. O servidor processa a solicitação e prepara a resposta.
  5. O navegador interpreta o resultado e solicita outros recursos necessários para apresentar a página.

HTTP é sem estado: não mantém automaticamente uma memória das visitas. Cookies e mecanismos de sessão podem relacionar requisições a um usuário, por exemplo, após um login.

3. Métodos GET e POST

GET: consultar um recurso

GET solicita a representação de um recurso. Exemplos: abrir uma página, carregar uma imagem e consultar resultados de uma busca. Parâmetros podem aparecer na URL, como /busca?tema=http.

GET é considerado seguro no sentido do protocolo: sua finalidade é consultar, sem solicitar uma alteração no servidor. Também é idempotente: repeti-lo deve ter o mesmo efeito pretendido de uma única solicitação, embora o conteúdo retornado possa mudar. Esses termos não significam criptografia.

POST: enviar dados para processamento

POST envia dados para o servidor processar conforme as regras do recurso. É comum em cadastros, envio de mensagens e criação de pedidos. Os dados costumam ir no corpo da requisição.

POST não é idempotente por definição: repetir um envio pode criar duas mensagens ou dois pedidos. O cabeçalho Content-Type informa o formato do corpo, como dados de formulário ou JSON.

GET consulta; POST envia dados para processamento. Dados sensíveis não devem ser colocados em parâmetros da URL, que podem aparecer no histórico e em registros. Em ambos os métodos, a proteção em trânsito depende de HTTPS.

4. Exemplos de requisição HTTP

Os exemplos são didáticos e usam a representação textual do HTTP/1.1. HTTP/2 e HTTP/3 mantêm conceitos como métodos e status, mas usam outro formato de transmissão. O domínio example.org representa um servidor de exemplo.

Requisição GET

GET /http.html HTTP/1.1
Host: example.org
Accept: text/html
  • GET: método utilizado para consultar.
  • /http.html: caminho do recurso solicitado.
  • HTTP/1.1: versão usada na mensagem ilustrada.
  • Host: identifica o servidor de destino.
  • Accept: informa um tipo de conteúdo aceito.

A linha vazia encerra os cabeçalhos. Neste exemplo de GET, não há corpo de requisição.

Requisição POST

POST /mensagens HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Content-Length: 23

nome=Breno&assunto=HTTP

O corpo contém os campos nome e assunto. O caractere & separa os pares de campo e valor; Content-Length informa o tamanho do corpo em bytes. Um servidor com a rota /mensagens precisaria receber, validar e processar esses dados.

Este bloco apenas mostra uma mensagem: não envia dados. Uma página estática de HTML precisa de um serviço de processamento para receber um formulário enviado por POST.

5. Exemplo de resposta HTTP

Para ilustrar uma resposta ao GET, considere que o servidor devolveu o pequeno documento HTML abaixo: 

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 124

<!DOCTYPE html><html lang="pt-BR"><head><meta
charset="UTF-8"><title>Exemplo</title></head><body><h1>Ola!</h1></body></html>
  • 200 OK: a solicitação foi atendida com sucesso.
  • Content-Type: o corpo contém HTML codificado em UTF-8.
  • Content-Length: número de bytes do corpo ilustrado, sem uma quebra adicional ao final.
  • A linha vazia separa os cabeçalhos do corpo; o corpo contém o documento que o navegador poderá interpretar.

O HTML aparece como texto neste exemplo porque os caracteres de marcação foram escapados. Na comunicação real, o servidor transmite os caracteres do documento, sem esse escape didático.

6. Códigos de status HTTP

O primeiro dígito indica a categoria: 1xx, informação; 2xx, sucesso; 3xx, redirecionamento; 4xx, erro relacionado à solicitação; e 5xx, erro no servidor.

Significado e exemplo de sete códigos HTTP
Código Nome Significado e exemplo
200 OK Sucesso. Exemplo: a página solicitada foi entregue.
301 Moved Permanently O recurso ganhou um endereço permanente. O cabeçalho Location indica o destino.
302 Found Redirecionamento temporário. Exemplo: enviar o visitante a uma página temporária de campanha.
400 Bad Request O servidor não pode ou não quer processar a mensagem por um erro percebido na solicitação, como sintaxe inválida.
403 Forbidden O servidor entendeu, mas recusou atender. Exemplo: acesso negado a uma área restrita.
404 Not Found O recurso não foi encontrado ou o servidor não deseja revelar sua existência. Exemplo: caminho de página inexistente.
500 Internal Server Error Uma condição inesperada impediu o atendimento. Exemplo: falha interna na aplicação do servidor.

O status informa o resultado, mas nem sempre revela a causa completa. Um erro de DNS ou uma conexão recusada pode acontecer antes de existir qualquer resposta HTTP.

7. Como observar HTTP na prática

  1. Abra uma página publicada por HTTP ou HTTPS.
  2. Abra as ferramentas do desenvolvedor do navegador e selecione a aba Rede ou Network.
  3. Recarregue a página e selecione a solicitação do documento.
  4. Observe URL, método, status, cabeçalhos e conteúdo da resposta. Outras linhas podem corresponder a imagens e arquivos.

Ao abrir este arquivo diretamente no computador com file://, a leitura é local e não demonstra uma troca HTTP com um servidor. Use uma versão hospedada para observar a comunicação descrita.
